# Groups Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Any person can make a group for their class; editors make lessons in it as drafts and publish them; members add a lesson and practise it from their own Today without copying anything; edits never silently clash; deletes wait 30 days; the group has its own storage.

**Architecture:** A root row belongs to a person **or** a group (`team_id` beside `user_id`, exactly one set). A `Space` type (`Wall | TeamSpace`) replaces `Wall` in the content data functions, so the compiler finds every place that still assumes "a person". Who may see or change a group row is one module (`access.ts`) built on one derived set (what a person can reach through published lessons). A member's practice is their own `exercises` rows pointing at group rows ("entries"), one per person per target. History is a change log written in the same transaction as the change; Recently deleted is a trash table of snapshots, so no reader of videos, sections or links changes.

**Tech Stack:** SvelteKit 2 / Svelte 5, TypeScript, Drizzle + better-sqlite3, Vitest, Tailwind 4, `qrcode` (already a dependency).

**Spec:** `docs/superpowers/specs/2026-11-02-groups-design.md` — read it first, with its mockups (<https://claude.ai/artifact/MKVZbXFexBrUVvPPUHg1Xj>). Also `CLAUDE.md` (hard rules), `docs/superpowers/specs/2026-11-02-accounts-design.md` (the owner wall this extends), `docs/superpowers/specs/2026-10-31-redesign-design.md` (the look), and `src/lib/server/scope.ts`.

## Naming: "group" is already taken in the code

`figure_groups`, `figures.group_id`, `getGroup`, `listGroupVariations` and `requireGroupInWall` all mean **a figure** (the figure that holds variations). A class group cannot be `group_id` without two meanings for one word in the same queries. In code the new thing is a **team** (`teams`, `team_id`, `TeamSpace`, `src/lib/server/teams.ts`, `src/lib/teams/`). Every word a person reads still says **group**. Routes say `groups` (`/[dance]/groups/[id]`), since a route is something a person sees.

## Structural risks found while planning, and how the plan closes them

Each of these would have shipped as a bug or a leak if the spec were built literally on today's code. The task that closes each is named.

1. **A group row with a person's id is charged to and listed for that person.** `usedBytes`, Today, Moves and every list filter by `user_id`. If a group row carried its maker's `user_id`, the maker's storage would pay for the group and their lists would show group things. → Group rows have `user_id = NULL` and `team_id` set; "who made it" lives in History, not in `user_id`. Exactly one of the two is set, checked by `ownerIntegrity` (Task 2). Today `wallOfRow` turns a null owner into `''` (`figures.ts:45`), and `lessonWall` returns null: both are replaced by `spaceOfRow`, which throws (Task 3).
2. **Code assumes one exercise per target.** `getLesson` (`lessons.ts:269`), `getFigure` (`figures.ts:538`) and the routine page (`routines/[id]/+page.server.ts:118`) take *the first* exercise of a lesson, figure or routine. With members, they would show another member's practice settings. The lesson page's figure and routine lists `leftJoin` exercises on the target, which would repeat each row once per member. `addFigureExercise` refuses when *anyone* has an exercise for the figure, so a second member could never practise it, and it copies the figure's owner (null for a group figure). → Every lookup becomes "**my** entry": `exercises.user_id = me`. A unique index per (person, target) makes a second one impossible; it was checked on today's production copy (0 duplicates) (Tasks 2, 4).
3. **A group lesson would create a review exercise nobody owns.** `createLesson` and `createRoutine` make a practice exercise in the same transaction. In a group that exercise would be the group's, practised by no one, and would trip risk 2. → Group lessons and routines get no exercise of their own; each person's Add makes theirs (Task 3).
4. **"Added" is not the same as "has entries".** The Add sheet lets a member untick the lesson itself and keep only a drill, and figures are unticked by default. Inferring "added" from entries would then lose the lesson from their Lessons list and lose a former member's access. → An explicit `lesson_adds` table (Task 2, 9).
5. **Removing one lesson must not take another lesson's drill off Today.** A drill or routine can be in two lessons. → Remove archives only the entries that no other lesson the person still has includes (Task 9).
6. **Restore brings back too much.** Archiving a group lesson archives every member's entries for it, as today's archive cascade does. Restoring must not revive an entry a member had removed earlier on their own. No unarchive exists today. → An entry comes back only if its `archived_at` equals the target's (one transaction writes one `now`). Restoring something whose name is now taken is refused with the name (Task 13).
7. **What a member sees must be closed under "contains".** A published lesson includes a routine. That routine embeds a child routine whose slots name figures, and a figure page shows its sibling variations. A direct set alone has two failure modes: the routine page names figures that 404 when tapped, or a figure page leaks a variation that only a draft has. → `reach()` is one closure: lesson → its figures (hand and via sections) and their recordings, routines → embedded routines → slot figures, drills (Task 7). For a member, a figure page lists only the variations in reach.
8. **A group drill holding a personal song.** Songs are personal. A group drill with the editor's `song_id` would play the editor's song to members. It would also block the editor's song delete ("refused while a live exercise uses it") for a reason they cannot see. → Group rows never hold `song_id`, and entries start with no song (Task 3, 9).
9. **A drill entry cannot be a copy, yet Today reads `exercises.name`.** → A new source `'added'` with `drill_id`. Its name is synced on rename and its archive follows the drill: this is the rule a figure's exercise already follows (`syncExerciseNames`). Content (notes, links, sections) is read from the drill. The "drills only" checks test `source = 'custom'`, so an entry can never itself be linked to a section (Task 9).
10. **Soft-deleting the hard-delete kinds touches every reader.** A `deleted_at` on videos, sections, links, section links and recordings would need a filter in some forty queries; one miss and a deleted section still plays or still links. → Deletes stay real deletes. A group delete first writes a snapshot of the rows (and keeps the file) into `team_trash` for 30 days. Restore re-inserts the rows with their old ids; `AUTOINCREMENT` never reuses an id. No reader changes (Task 13).
11. **The player's 0.1 s nudges.** Version numbers would make a person clash with their own last nudge whenever a response is slow, and History would log every nudge. → The clash check compares *values* (the save carries what it saw), not versions. History merges changes by the same person to the same field of the same thing within 10 minutes (Tasks 11, 12).
12. **Group uploads would have no limit.** The upload routes call `roomFor(db, lesson.userId!)`; for a group lesson that is null, so the uploader's own room or no limit would apply. → `roomForOwner(space)`; group rooms come in Task 7, before any group can upload (Task 7).
13. **Group limits multiply past the disk.** Each person may own 2 groups, each worth 200 MB per person in it. If 15 people all join all 30 groups, that is 30 × 3 GB = 90 GB on a server with 22 GB free. A group of one is also 200 MB free beyond your own limit, and handing groups over could dodge the 2-group limit. → Handing over is refused when the new owner already owns their limit (Task 5). Every upload is also refused when it would leave the disk under **2 GB free**, whatever the limits say (Task 7). *(Calls made here; see the summary for the user.)*
14. **Make my own copy breaks unique names.** Figure names are unique per person and dance. Copying "Enchufla" to someone who has an "Enchufla" would break that. → The copy's variations join the person's figure of the same name (folded); a variation name already taken gets " (Salsa nadaljevalna)" appended; routines likewise. Files are hard links: no extra disk, charged in full (Task 16).
15. **The join link has no public page.** `PUBLIC_PATHS` is an exact-match set, and the "no account" sentence must reach someone who is not signed in. → `/g/[code]` stays private. A signed-out visitor is sent to `/login?next=/g/…` (the existing redirect), and Sign in shows the no-account sentence when `next` is a group link. The group's name is never shown to anyone not signed in (Task 6).
16. **The spec contradicts itself in four places**, from before the mockup decisions:
    - "No fifth tab" (Constraints);
    - the group page "reached from the Lessons tab";
    - "under a **Group / Mine** filter" (Add);
    - "the Lessons tab's groups" (deleting a group).

    → Fixed in the spec in this plan's commit, to match "Decided from the mockups".
17. **"1 new drill · Add" would never go away** if the member does not want it. → `lesson_adds.seen_at`: what was added to the lesson after it is "new"; confirming the Add sheet or tapping "Not now" moves it (Task 9).
18. **Undo in the video player re-creates a section as a new row.** That would leave a twin in Recently deleted. → In a group, the player's Undo calls Restore on the trash entry the delete returned (Task 13).

### Found by the plan's review (a fresh reviewer, checked against the code)

19. **The routes delete files, not the data functions.** The lesson page's `deleteVideo` action unlinks the file after `deleteLessonVideo` (`lessons/[id]/+page.server.ts:380`), and the figure page does the same for recordings. A trash snapshot would point at a file that is already gone. → In a group, the route skips the unlink when the delete returned a trash id; a route-level spec checks the file survives (Task 13).
20. **A page a member may open still sends draft content in its data.** The figure, routine and lesson pages build their side lists from the whole space: taught in, routines using, leads to, sections, labels, pickers. `videosOf` returns every video of the owner. The Link popup's `GET` returns every option. Hiding controls is not enough. → In read mode every list is built from `reach`, or left out. The Link popup's `GET` needs `edit`. The matrix asserts that the member's page data holds no title or id that only a draft has (Task 8).
21. **Entries made from ids in the request.** `addLesson`'s picks and `addFigureExercise`'s figure id come from the form. Practice content then reads the target by id, so a posted id would hand anyone another person's notes and sections. → `addLesson` needs a published lesson the person can read, and picks ⊆ that lesson's reach. `addFigureExercise` needs read access to the figure. The practice content of an entry is read only while its target is in reach (Tasks 4, 9).
22. **Logs could land on a group's own drill row.** Sets, the practice endpoint and the player's save guard with `requireExerciseInWall`. Swapping in an access guard would let sets go onto a row everyone shares. → Logging and practice settings stay personal-only (`Wall`) on the person's own entry. A group drill's page shows the viewer's entry for it (Tasks 7, 8).
23. **The archive cascades overwrite entries already archived.** `archiveLesson`, `archiveRoutine` and `archiveVariation` set `archived_at` on every exercise of the target. That would re-stamp an entry a member had removed earlier, and Restore would then revive it, defeating risk 6. → Every cascade adds `archived_at is null` (Task 4).
24. **A member could link their entry into their own lesson.** `linkExercise` checks the exercise's own owner, and an entry is the member's. → The cross-owner check uses the entry's *target's* owner, and personal pickers leave out entries whose target is a group's (Task 3).
25. **Entries outlive reach.** An editor unlinks a drill from the lesson, or archives the lesson. The members' entries for it stay live, and Remove no longer catches them. → `reconcileEntries` archives a team's entries that are out of the person's reach, in the same transaction as any group change that can shrink reach (Task 9).
26. **An entry drawn with personal-only helpers.** The player builds a group routine's shapes, names and graph from the member's own wall. `practice-content.ts`'s `exerciseWall` uses the entry's owner. `lessonDays` misses added lessons. The picker's `flat('custom')` drops `'added'` entries. The exercise page shows Rename and Archive for them. → All read through `spaceOfRow(target)` and handle `'added'` (Tasks 3, 10).
27. **The clash check can be skipped.** "A form without `seen` is accepted" means any save path that forgets `seen` overwrites silently. → On group rows, `seen` is required (Task 11).

Smaller ones, folded into their tasks:
- the YouTube save's room check runs at request time in `link-form.ts` (Task 7);
- songs and count takes need the disk floor too (Task 7);
- open storage requests are keyed by person and team (Task 14);
- restoring a section link that has since been re-made is refused as `exists` (Task 13);
- a member gets 404 on Recently deleted (Task 13).

## Global Constraints
